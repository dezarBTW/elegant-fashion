# Product shopping and admin notifications

- Add or edit products in **Admin → Products**. Enter a description and select the available sizes: S, M, L, XL and XXL. New products require at least one size. Uncheck every size when editing to stop new purchases while keeping the detail page and request form available.
- Product cards link to `/ready-to-wear/product/[slug]` through the image and name; they have no purchase buttons. Customers choose size and quantity on the detail page, then use **Add to cart**. The navbar cart drawer allows size and quantity changes; there is no separate cart page. All five sizes stay visible and unavailable options are disabled. Checkout shows the chosen size and quantity in its summary, with edit buttons that open the cart drawer; payment still validates size availability on the server. The cart groups the same product and size together; different sizes retain separate quantities.
- Admins select **Male fashion**, **Female fashion** or **Unisex (both)** when adding or editing a product. The shop's **Gender** dropdown filters All / Male fashion / Female fashion; unisex products appear in both gender filters. Existing unclassified products remain in All until an admin chooses their gender. Garment categories remain separate for category browsing and recommendations.
- Size availability and prices are checked again on the server before a new checkout. The selected size is stored in the order and appears in admin orders, customer order history, receipts and fulfilment emails.
- Guests can browse and build a cart. Continuing to checkout requires sign-in and preserves the cart; password sign-in, Google sign-in and account confirmation return checkout visitors to checkout. The checkout API verifies an active, confirmed account, binds new orders to its user ID, and rejects attempts to resume another account's checkout. Checkout's **Back to shop** link returns to Ready-to-wear.
- Recommendations show at most six other active, available products from the same category. Shared description/name terms, price proximity and featured status determine their order. The candidate query is capped at 100 products from that category.
- Customers can submit a different-size or colour request without signing in. Requests are stored privately and emailed only to **elegantyoufashion18@gmail.com**. They are enquiries, not paid orders. Review them in **Admin → Size & colour requests**; a failed notification can be retried there.
- Successful student registrations send an admin notification to the same address. The student details dialog records email acceptance and offers a retry when none is recorded. Historical registrations without a saved status are labelled unconfirmed rather than assumed delivered.
- Transient service-email failures retry up to three times with the same Resend idempotency key. An accepted notification is recorded in the database; manually retrying a recorded notification does not send another email. Provider acceptance is not a guarantee of inbox delivery.
- Resend uses the existing server-side `RESEND_API_KEY` and `RESEND_FROM_EMAIL`; no additional environment variables are needed.

Database migrations: `supabase/migrations/20261021102019_product_sizes_and_custom_requests.sql` and `supabase/migrations/20261021125137_product_gender.sql`. The gender column accepts only `male`, `female` or `unisex` (or NULL for an unclassified older listing). The custom-request table has RLS enabled and is accessible only through the authorised server APIs. It is not directly readable by guests or signed-in customers.

Verification: `node --experimental-vm-modules --test scripts/*.test.mjs`, `npm run lint`, and `npm run build`. Browser verification uses isolated fixtures under the ignored `output/playwright/` directory so production products, students, orders and email recipients are not changed.
